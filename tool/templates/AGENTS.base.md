# Flutter 项目 Agent 指南

## 项目定位与范围

本项目是面向 Android 和 iOS 手机的 Flutter 单应用工程。它提供可运行、可测试、可裁剪的
工程底座，不预先实现具体产品业务，也不建设桌面、Web、平板专用布局、多产品 Workspace、
通用代码生成平台或自动发布系统。

所有 Agent 必须遵守以下原则：

1. 先理解现有源码、测试、配置、文档和工作区改动，再定义行为与验收条件。
2. 保持改动聚焦，只实现用户要求的最小完整能力，不为“以后可能需要”增加抽象、依赖或平台配置。
3. 同一类能力只保留一套默认实现，不并行维护多套状态管理、路由、网络或存储方案。
4. 示例 Feature 必须可以完整删除，基础设施不得依赖具体示例或具体产品规则。
5. 新依赖必须解决明确问题，并评估维护状态、许可证、平台支持、包体影响、替换成本和版本兼容性。
6. 不覆盖、回退或重新格式化用户已有的无关改动；遇到重叠修改时先理解并在其基础上工作。

## 目录与依赖边界

```text
lib/
├── main.dart                     # 最小入口，只选择环境并启动应用
├── app/                          # 启动、配置、国际化、路由、主题和全局组装
├── core/                         # 网络、存储、错误、日志等稳定基础能力
├── features/                     # 按业务能力纵向组织的 Feature
└── shared/                       # 无业务语义的跨 Feature 资源、布局和组件
assets/                           # 图片、普通 SVG、图标源、字体和品牌源
config/                           # 可提交示例配置与被忽略的本机配置
test/                             # 尽量镜像 lib/ 边界组织的测试
tool/                             # 当前工程专用的生成与质量检查工具
docs/                             # 工程指南和架构决策记录
```

依赖方向必须清晰：

1. `app/` 可以组装 `core/`、`features/` 和 `shared/`。
2. Feature 只依赖公开的 `core/`、`shared/` 契约，不导入 `app/` 或其他 Feature 的内部实现。
3. `core/` 与 `shared/` 不得反向依赖 `app/` 或具体 Feature，也不得包含具体产品规则。
4. `shared/` 只接收已经确认被多个 Feature 复用且没有业务语义的内容，不作为临时代码堆放目录。
5. Dio、go_router、存储插件、日志插件和屏幕适配插件的类型只能存在于各自 adapter 边界；
   Feature 消费项目自有接口，不直接依赖插件 API。
6. `tool/` 中每个生成器只管理自己声明的固定输入和输出，不得扩展成可以执行任意模板的通用 CLI。

## 已启用能力与边界

本项目当前只按既有实现使用以下增强能力，新增或替换实现时必须维持各自边界：

1. 国际化使用 Flutter 官方生成链，初始维护 `en`、`zh`，用户可见文案通过类型安全 API 访问；
   Feature 不反向依赖应用层生成类。
2. 单色语义 SVG 图标以原始 SVG 和稳定清单为人工维护源，OTF 与 Dart `IconData` 为生成产物；
   普通、多色或动态图仍走普通 SVG 资源，不强行放入字体。
3. 认证通过项目自有会话、网络和安全存储接口实现；默认不接真实服务端或第三方登录，密码、
   access credential 和 refresh credential 不得进入普通偏好、日志、错误或截图。
4. 品牌工具只转换和校验已获授权的源资源，三个环境共用一套 Android/iOS 图标与启动资源；
   中立占位资源不得被描述为正式品牌，工具不负责设计 Logo。
5. 手机屏幕适配通过项目设计单位统一表达；不为桌面、平板、折叠屏或通用断点体系增加默认复杂度。

## 实施工作流

1. 修改前阅读相关实现、测试、配置和文档，并用 `git status`/diff 确认已有改动边界。
2. 先写清正常行为、关键边界、主要失败路径和可验证的验收条件，再修改实现。
3. 新增依赖前记录选择理由、替代方案、许可证、平台要求、升级验证和回滚方式。
4. 对外暴露项目自有稳定接口，把插件类型、传输模型和平台异常限制在 adapter 内部。
5. 环境差异必须来自显式配置，不得用散落的 `kDebugMode` 或平台判断隐式改变业务语义。
6. 修改实现时同步更新相关测试、详细中文注释、示例、生成产物和工程文档。
7. 变更生成输入后使用该能力的固定生成命令重新生成，不手工修改带生成标记的文件。
8. 按风险执行格式、静态分析、测试和必要平台构建；不能执行的验证必须说明原因和剩余风险。

## 常用命令

在 Flutter 工程已经创建且依赖可用时，从项目根目录执行：

```bash
flutter pub get --enforce-lockfile
flutter run --flavor dev --dart-define-from-file=config/dev.example.json
dart run tool/generate_localizations.dart --check
dart run tool/generate_icon_font.dart --check
dart run tool/generate_branding.dart --check
dart run tool/generate_agents.dart --check
dart tool/ci/check_documentation.dart
dart format --output=none --set-exit-if-changed .
flutter analyze --fatal-infos --fatal-warnings
flutter test
flutter build apk --debug --flavor dev --dart-define-from-file=config/dev.example.json
```

不得把未执行的命令报告为通过。涉及原生平台、字体、应用图标、启动资源或构建配置时必须执行
对应平台的实际构建；非 macOS 主机只能报告 iOS 静态检查，不能声称完成 Xcode 构建。

## 注释与文档规范

本项目要求生成到项目中的代码注释使用中文。脚手架仓库自身的工具实现可以保留必要的英文
术语或上游原文，但任何生成的 Dart 代码、示例和项目规范都必须提供准确、可维护的中文说明。

以下内容必须使用 Dart 文档注释 `///`：

1. 对外公开的类、扩展、函数、属性和可复用 Widget。
2. 状态管理单元、Repository 接口、网络拦截器、存储接口、错误类型和配置模型。
3. 框架扩展点、生命周期入口，以及需要调用方遵守约束的 API。
4. 行为无法仅从名称和类型准确推断的私有抽象。

详细文档注释应按实际复杂度说明目的、职责边界、明确不负责的内容、参数、返回值、状态变化、
副作用、错误转换、初始化与释放顺序、异步时序、并发限制、缓存或重试规则、安全约束、平台差异
和调用方必须维持的不变量。非直观用法应给出最小示例。

以下逻辑必须在关键分支前用行内注释解释原因：

1. 非显而易见的业务规则、边界条件和失败降级策略。
2. 状态机转换、缓存失效、去重、重试、请求取消和迟到结果处理。
3. 异步或并发顺序，以及顺序改变后可能出现的竞态。
4. 平台差异、第三方 API 异常行为、兼容处理和临时 workaround。
5. 数据修正、时间或单位换算、序列化兼容、安全过滤以及性能或包体取舍。

注释优先解释 `why`、约束和取舍，再补充调用者需要的 `how`。不得逐句翻译代码，也不得为
简单赋值、常规 getter/setter、直观 Widget 层级或明显空值判断制造噪声。临时方案必须记录
触发条件、移除条件和可追踪的 TODO/Issue；注释与实现冲突时必须在同一变更中修正。

## 测试规范

测试是完成条件，不是可选收尾工作：

1. 测试文件使用 `*_test.dart`，并尽量镜像 `lib/` 的目录边界。
2. 新功能至少覆盖正常路径、一个关键边界和一个主要失败路径；修复缺陷必须保留回归测试。
3. 网络、时间、随机数、存储、平台通道和环境配置必须可替换；测试不得访问真实服务、密钥或设备数据。
4. 网络重点覆盖请求配置、错误映射、取消、敏感信息过滤、凭据注入和认证重放边界。
5. 状态管理重点覆盖加载、成功、空数据、失败、重试、并发、销毁和迟到结果。
6. 路由重点覆盖参数解析、未知页面、重定向、恢复期和不安全返回地址。
7. 存储重点覆盖默认值、读写失败、清理、schema 兼容以及凭据不得进入普通存储。
8. 可复用 Widget 至少验证关键状态、交互、无障碍语义、窄屏、大字体和操作可达性。
9. 生成器测试必须验证相同输入字节稳定、陈旧产物、非法输入和失败恢复；写入测试只使用系统临时目录。
10. 测试必须确定且可独立运行，不依赖执行顺序，不使用无依据延时，也不以“没有异常日志”代替断言。

提交交付前原则上依次执行格式检查、严格静态分析和全量测试。随机顺序失败必须记录 seed 并
修复共享状态或资源释放问题，不得固定顺序掩盖缺陷。Golden 更新前必须先通过布局矩阵并逐张
审查实际差异，不能用更新命令直接接受未知像素漂移。

## 移动端屏幕适配

1. 唯一参考设计尺寸为 `375 x 812`，默认只支持 Android/iOS 手机。同一应用不得按页面、
   环境或 Feature 使用不同设计宽度。
2. `flutter_screenutil` 只能由应用根部和项目自有适配层使用。Feature 与共享组件必须通过
   项目 `du`/`dsp` 表达设计稿尺寸，不得直接散落 `.w`、`.h`、`.sp` 或插件类型。
3. 宽、高、间距、圆角和图标统一按宽度比例换算，避免矮屏被独立纵向拉伸。系统文字缩放必须
   保留，不得全局使用 `TextScaler.noScaling`。
4. SafeArea、状态栏、刘海、横屏侧边、底部手势区和键盘 `viewInsets` 使用平台实测逻辑值，
   不得传入 `du`/`dsp`，也不得由父子 Widget 重复消费。
5. 短屏、大字体、横屏或键盘导致内容增长时，正文和主要操作必须可以滚动到达；不得通过压缩
   文字、隐藏溢出或独立高度比例维持截图外观。
6. 固定视觉画布只允许用于明确的海报或活动视觉场景，并在局部说明设计尺寸、裁切与安全内容区。
   `contain`/`cover` 不得用于表单、列表、导航、状态页或普通交互布局来掩盖适配问题。
7. 触控目标应维持可访问的逻辑像素下限；视觉尺寸可以换算，但不能随窄屏缩到不可操作。
8. 布局测试至少覆盖 `320x568`、`360x800`、`375x812`、`390x844`、`430x932` 和
   `800x360`，并覆盖 200% 系统文字、四边安全区、动态键盘 Insets、滚动可达性、关键矩形、
   语义与必要 Golden。
9. 测试必须向 FlutterView 和 MediaQuery 注入一致的真实平台值，并在 teardown 重置 View；
   不得只调用 `setSurfaceSize` 后假定底层适配器读到了相同尺寸。
10. 新增页面首先选择普通约束、滚动和项目设计单位；只有职责明确且有专项测试时才新增布局抽象。

## 密钥与安全

1. 禁止提交 API Key、Token、证书、私钥、密码、真实用户数据、生产凭据或内部地址。
2. 示例配置只能使用明显无效的占位值；本机配置必须被忽略，且 Dart define 仍不得承载长期凭据。
3. 日志、错误、诊断字符串、测试快照和 Golden 必须脱敏，不输出原始 URL、请求正文、凭据或完整个人数据。
4. 认证凭据只能进入项目安全存储边界；普通偏好只保存语言、主题等非敏感设置。
5. 涉及删除、覆盖、签名、发布、生产配置、外部系统写入或真实品牌替换时，先确认授权和精确范围。
6. 生成器先验证所有输入，再触碰固定白名单输出；失败必须恢复旧版本或保留明确的人工恢复证据。

## Git 与外部操作

1. 除非用户明确要求，不创建 commit、不暂存、不推送、不发布，也不修改外部系统。
2. 用户已有改动均视为用户资产；不得使用破坏性命令回退、覆盖或清理无关文件。
3. 用户明确要求提交时才使用 Conventional Commits，并在提交前检查 diff 与验证结果。
4. 不把构建产物、临时目录、真实配置、凭据、Goal 审计目录或无关生成文件混入提交。
5. 破坏性变更必须提供迁移和回滚说明；可以保持兼容时，不无理由改变公开接口。

## 完成定义

一项需求只有同时满足以下条件才可以标记完成：

1. 实现符合用户需求和已确认范围，没有夹带范围外能力。
2. 公开 API、复杂逻辑、平台限制和关键取舍具有准确且足够详细的中文注释。
3. 正常、边界和主要失败行为得到与风险相称的测试覆盖。
4. 格式、严格静态分析、相关测试及必要平台构建通过，或已明确记录无法执行的原因。
5. 示例、配置模板、生成产物和工程文档与实现同步。
6. 不包含真实密钥、凭据、个人数据、内部或生产地址及敏感日志。
7. 最终 diff 没有覆盖用户改动、无关重构、手改生成文件或意外产物。
8. 已说明剩余风险、平台验证缺口、升级边界和必要回滚方式。
