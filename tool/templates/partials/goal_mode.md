## Goal Mode 工作流

只有用户明确输入 `/goal`、明确要求进入 Goal Mode，或客户端已经将当前任务置于 Goal Mode 时，才启用本流程。普通开发请求不得自行创建 Goal。

### Goal 初始化

1. 使用客户端提供的 Goal 工具注册用户的完整目标；仅在目标确实完成或满足工具规定的阻塞条件时更新最终状态。
2. 在当前项目根目录查找已有 `goal-[num]/`，使用下一个递增编号创建新目录，不得覆盖已有 Goal。
3. 创建以下三个文件：

```text
goal-[num]/
├── input.md
├── plan.md
└── tasks.md
```

4. `input.md` 必须逐字保存用户触发 Goal 的原始输入，不得改写、摘要或补充推测。
5. `plan.md` 必须记录需求分析、阶段范围、验收条件、上下文、明确假设、风险、执行方案、验证方式和回滚方案。
6. `tasks.md` 必须把计划拆分为小而可独立验证的任务。每个任务预留状态、实现记录、验证证据、剩余风险和下一步字段，并提前标出每三个任务后的全面检查节点。
7. Goal 初始化完成前不得修改业务源码、工程配置或依赖。
8. 第一轮只完成 Goal 注册和上述文件初始化，然后只输出 `GOAL_INIT_DONE` 并结束本轮，让客户端继续推进。

### 每轮执行

1. 每次新会话或上下文压缩后，完整读取当前 Goal 的 `input.md`、`plan.md` 和 `tasks.md`。
2. 使用可用的计划或 Todo 工具登记本轮工作，只选择 `tasks.md` 中第一个未完成任务。
3. 每轮只执行一个任务，不提前实现后续任务，也不擅自扩大目标范围。
4. 修改前确认任务验收条件；修改后检查源码、注释、测试、diff、日志、静态分析和必要构建证据。
5. 不得只口头声称“100% 有信心”。如果证据不足，继续诊断、补测试或修正实现，直到达到与风险相称的高置信度。
6. 完成任务后更新 `tasks.md`，记录实际变更、执行过的命令、结果、剩余风险和下一任务。
7. 除非用户在 Goal 中明确要求，Goal Mode 也不得自动创建 commit、推送、发布或修改外部系统。
8. 每轮结束时向用户简短汇报当前任务和验证结果，然后停止输出，由客户端决定是否继续下一轮。

### 全面检查节点

每完成三个实现任务，执行一次跨任务检查，并把证据写入 `tasks.md`：

1. 需求和阶段范围是否发生偏离。
2. 架构依赖、公开接口和删除可选模块的能力是否仍然成立。
3. 是否存在逻辑缺陷、竞态、资源泄漏或未处理错误。
4. 格式、类型检查、静态分析、测试和构建是否通过。
5. UI 是否在代表性尺寸下无溢出、遮挡和异常状态缺失。
6. 安全、隐私、日志脱敏和配置隔离是否正确。
7. 数据一致性、缓存、迁移和回滚策略是否充分。
8. 注释、示例、生成产物和文档是否同步。

### 阻塞与无人值守约束

Goal Mode 默认按无人值守方式推进。遇到不影响目标方向的不确定信息时，选择安全且最小的合理假设，写入 `plan.md` 或 `tasks.md`，继续不依赖该信息的部分。

如果继续操作需要新的用户授权、真实凭据、破坏性操作、生产环境变更或会实质改变目标方向，不得自行猜测或绕过限制；记录阻塞证据，并按客户端 Goal 工具的规则处理阻塞状态。

Goal Mode 中禁止：

1. 抢占用户设备焦点或启动未经要求的 GUI。
2. 重启本机、关闭网络或影响用户其他进程。
3. 删除重要数据或使用未经确认的破坏性命令。
4. 修改生产配置、真实密钥、认证、支付、签名或发布状态。
5. 在 Goal 初始化完成前修改项目实现。
6. 一轮执行多个任务或跳过第一个未完成任务。
7. 擅自扩大需求范围或添加本项目明确排除的功能。
8. 伪造测试、构建、文档核对或外部系统验证结果。

### Goal 完成

所有任务完成后必须执行最终全面 Review，从用户体验、需求范围、架构、代码、注释、安全、隐私、错误处理、数据一致性、测试、构建、文档和回滚角度检查整个目标。

修复所有已知高风险问题并记录最终证据后，才可以把 Goal 标记为完成。最终报告应简洁说明已交付内容、验证结果、剩余的非阻塞风险和必要的后续动作。
