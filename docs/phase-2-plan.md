## 屏幕适配决策

### 目标

屏幕适配的目标是让一套手机设计稿在不同逻辑宽度的 Android/iOS 手机上保持
相同的视觉比例、层级和操作路径。它不是面向手机、平板、桌面的通用响应式
框架，也不承诺在不同比例屏幕上同时做到无裁切、无留白、无滚动和完全相同。

默认参考设计尺寸为 `375 x 812` 逻辑像素。采用项目时可以在唯一配置入口修改
参考尺寸，但同一个应用不得按页面或环境使用不同设计宽度。

### 默认实现

选择 `flutter_screenutil ^5.9.3` 作为底层实现，原因如下：

1. `designSize`、宽度缩放和字体缩放直接覆盖固定手机设计稿的需求。
2. Dart 最低要求为 2.17，可用于当前 Dart 3.7 / Flutter 3.29 基线。
3. 依赖只有 Flutter，Apache-2.0 许可证允许模板使用和再分发。
4. 相比项目自建的进程级可变单例，它已经处理根节点初始化和屏幕指标变化，
   可以减少初始化遗漏、旋转后比例陈旧和测试状态泄漏风险。

该选择也有明确代价：5.9.3 稳定版发布距今较久，发布者未认证，并且直接在
Feature 中散布 `.w`、`.h`、`.sp` 会形成较高替换成本。因此必须遵守以下边界：

1. `app/` 负责 `ScreenUtilInit` 和唯一参考尺寸的组装。
2. `shared/layout/` 暴露项目自有的设计单位，例如 `du` 和 `dsp`；Feature 不得
   直接导入 `flutter_screenutil`。
3. `du` 始终使用宽度比例，宽度、高度、间距、圆角和图标共用同一比例。
4. `dsp` 在设计字号基础上应用设计比例，同时保留 Flutter 的系统文字缩放。
5. 不提供独立的高度单位；禁止用屏幕高度比例拉伸控件和纵向间距。

`flutter_screenutil_plus` 不作为默认方案。2026-08-10 复核时的最新稳定版为
1.5.0，依赖解析要求 Dart 3.10.1，与项目 Dart 3.7 基线不兼容；其断点、
Size Class、桌面和嵌套布局能力也超出仅手机设计稿缩放
的范围。本次复核证据见 ADR 0014；后续升级仍必须重新核对版本、许可证、维护状态和
SDK 约束，不得在没有迁移证据时静默替换默认方案。

### 强制布局规则

1. `SafeArea`、状态栏、Home Indicator、系统手势区和键盘 `viewInsets` 使用
   Flutter 报告的真实逻辑值，不经过 `du` 缩放。
2. 短屏通过 `ListView`、`CustomScrollView` 或明确的滚动容器保证内容和主要
   操作可到达；不得压缩整页高度或忽略溢出。
3. 长屏只扩展设计稿中明确标记的弹性留白，不把所有纵向间距按高度拉长。
4. 不锁定设备方向。横屏至少保证无溢出、内容可滚动和主要操作可用；除非具体
   页面设计明确要求，不建立另一套横屏视觉稿。
5. 海报、活动视觉或其他固定画布页面可以局部使用统一 `Transform.scale` 或
   `FittedBox`，但必须明确 `contain` 留白或 `cover` 裁切策略，不能成为表单、
   列表等普通页面的默认容器。
6. 位图必须提供足够分辨率并明确 `BoxFit`；SVG 和字体继续使用项目资源入口。
7. Android/iOS 使用同一应用字体和实际字重文件时，需要同步评估字体许可证、
   CJK 字体包体和回退字体差异；不得为了截图一致关闭系统无障碍字体缩放。

### 屏幕适配验收矩阵

Widget 测试至少覆盖以下逻辑视口：

| 场景 | 尺寸 | 目的 |
| --- | --- | --- |
| 最窄手机 | `320 x 568` | 暴露横向溢出和短屏不可达内容 |
| 常规 Android | `360 x 800` | 验证小于参考稿时统一缩放 |
| 参考设计稿 | `375 x 812` | 与设计稿和 Golden 基准对齐 |
| 常规 iPhone | `390 x 844` | 验证非整数比例和安全区 |
| 大屏手机 | `430 x 932` | 验证大于参考稿时统一缩放 |
| 手机横屏 | `800 x 360` | 验证可滚动、键盘和主要操作 |

每种核心页面至少验证正常文字和较大系统文字；表单还要覆盖键盘 Insets。验收
必须证明：没有布局异常，主要内容与操作可到达，关键元素相对设计稿按同一宽度
比例缩放，安全区没有被重复缩放。关键页面使用 Flutter 原生 Golden Test；布局
契约测试同时断言代表性元素的矩形位置，避免只依赖容易受字体渲染影响的截图。

## 品牌资源生成决策

### 目标与阶段边界

品牌资源生成接收用户准备并确认有权使用的源文件，将其转换为 Android/iOS 所需
的应用图标和启动资源。工具不设计、绘制或下载 Logo，也不把模板仓库的示例资源
作为下游项目的正式品牌资源。

项目名称、组织名、Android `applicationId` / `namespace`、iOS Bundle Identifier
和应用显示名称属于第一阶段“项目初始化”，不得延后到本任务。本任务只处理品牌
图片及其原生引用，不修改包名、签名、证书或发布配置。

`dev`、`staging`、`prod` 使用完全相同的 Logo、应用图标和启动资源。Android
flavor 应继承 `src/main/res` 中的公共产物，iOS scheme 应引用同一个 AppIcon 和
启动资源集合；不得生成环境角标、环境专属图片或三份内容相同的源文件。

### 源资源契约与生成工具

品牌源文件集中放在一个可提交、可替换的目录中，计划使用以下固定输入：

```text
assets/branding/
├── app_icon.png                  # 1024 x 1024 公共完整图标
├── app_icon_foreground.png       # Android Adaptive Icon 透明前景
├── app_icon_background.png       # Android Adaptive Icon 背景；也可由配置指定纯色
├── app_icon_monochrome.png       # 可选，Android 13+ 主题图标
├── splash_logo.png               # 启动页展示 Logo 时使用
└── LICENSE.md                    # 来源、权利范围与正式替换责任
```

应用图标默认参考 ZoiHK 的生成方式，选择精确锁定的
`flutter_launcher_icons 0.14.4` 作为仅开发期依赖；兼容性与许可证复核见 ADR 0014。配置
只保留根目录 `flutter_launcher_icons.yaml` 一个来源，不在 `pubspec.yaml` 再写
一份重复配置。只启用 Android 和 iOS，不生成 Web、Windows 或 macOS 资源。

Android 必须配置普通图标以及 Adaptive Icon 的前景和背景，并在资源允许时加入
Android 13+ 单色图标；前景图形必须位于系统蒙版安全区。iOS 图标必须填满画布，
生成结果不得包含 Alpha 通道。输入目录中的图片只作为生成源，除非应用运行时
确实使用，否则不加入 Flutter runtime assets，避免无意义增加包体。

`flutter_launcher_icons` 只负责应用图标。启动资源使用独立、精确锁定的
`flutter_native_splash 2.4.6`；其输入仍来自同一个 `assets/branding/` 目录，并遵守
所有环境共用一套资源的约束。不得把应用图标命令描述成启动页生成命令。

### 验收与防漂移

1. 生成前校验必需文件、PNG 格式、正方形尺寸、最低分辨率、Alpha 和 Adaptive
   Icon 安全区；错误输入必须在修改原生产物前失败。
2. 相同输入与配置必须逐字节生成相同产物；重复执行不得产生 diff。
3. CI 必须检测源文件或配置已经更新但 Android/iOS 生成产物仍陈旧的情况。
4. Android/iOS 的所有环境必须引用同一套公共产物，并检查不存在环境专属图标
   或启动资源目录。
5. Android 必须实际构建并核对 Manifest 图标引用；iOS 必须在可用的 macOS
   环境构建并核对 Asset Catalog。无法执行 iOS 构建时必须记录验证缺口。
6. 回滚只移除品牌生成配置、专用工具、源文件和对应生成产物，不影响包名、
   环境配置、签名或其他用户资源。

## 基础 AGENTS.md 生成决策

### 目标与边界

新项目应获得一份可直接使用的根目录 `AGENTS.md`，让后续 Agent 在不了解模板
历史的情况下也能遵守工程边界。这里的“自动生成”是指项目初始化流程调用一个
确定性的专用命令，不是在 `flutter run`、构建或应用运行时后台改写文件。

实现只允许包含：

```text
tool/
├── generate_agents.dart
└── templates/
    ├── AGENTS.base.md
    └── partials/
        └── goal_mode.md
```

推荐命令：

```bash
dart run tool/generate_agents.dart
dart run tool/generate_agents.dart --check
```

这不是通用脚手架 CLI。工具不得生成业务代码、依赖、平台工程、发布配置或任意
用户未授权文件。

### 生成内容

基础 `AGENTS.md` 至少包含：

1. 项目用途、支持平台和明确范围。
2. `app/core/features/shared` 目录职责与依赖方向。
3. 运行、格式化、静态分析、测试和必要构建命令。
4. 公开 API 文档注释和复杂逻辑行内注释要求。
5. 新功能、缺陷修复、Widget、网络、存储和环境配置的测试要求。
6. 密钥、日志、普通存储与安全存储约束。
7. 不覆盖用户改动、不自动提交、推送、发布或修改外部系统的 Git 规则。
8. 项目实际启用能力的使用边界；不得写入尚未启用的可选功能。
9. 移动端屏幕适配的参考设计尺寸、项目设计单位、系统 Insets、短屏滚动、
   固定画布边界和多尺寸验收要求。
10. 当前根目录 `AGENTS.md` 中完整的 Goal Mode 工作流，不得只保留摘要或链接。

生成文件不得包含真实包名、内部 URL、密钥、个人绝对路径或模板仓库的 Goal
执行记录。基础文件使用中文和 LF 换行，并包含生成来源与重新生成命令。

### 生成文件中的屏幕适配章节

第二阶段生成的基础 `AGENTS.md` 必须包含一节独立、可直接执行的“移动端屏幕
适配规范”，至少明确以下内容：

1. 应用只面向 Android/iOS 手机，默认参考设计尺寸为 `375 x 812`；项目修改
   参考尺寸时只能修改唯一配置入口，不得在页面或环境中定义不同基准。
2. Feature 只能使用项目公开的 `du/dsp` 设计单位，不得直接导入
   `flutter_screenutil`，不得在业务页面散布 `.w`、`.h` 或 `.sp`。
3. 宽度、高度、间距、圆角和图标统一使用 `du` 的宽度比例；不提供或使用独立
   高度缩放单位，避免不同比例手机上的几何变形。
4. 字号使用 `dsp`，同时保留 Flutter 的系统文字缩放；不得通过覆盖
   `MediaQuery` 或固定 `TextScaler.noScaling` 关闭无障碍字体缩放。
5. `SafeArea`、状态栏、Home Indicator、系统手势区和键盘 `viewInsets` 使用
   平台真实逻辑值，禁止再次经过 `du` 缩放。
6. 短屏内容必须可滚动且主要操作可到达；长屏只扩展设计稿标记的弹性留白，
   不按屏幕高度拉伸全部纵向间距。
7. 固定画布只用于海报、活动视觉等明确场景，并注明 `contain` 留白或 `cover`
   裁切策略；普通表单、列表和详情页不得默认整体 `Transform.scale`。
8. 适配测试至少覆盖 `320/360/375/390/430` 逻辑像素宽度、一个手机横屏、
   较大字体、安全区和键盘 Insets，并断言无布局异常及关键元素统一比例。

生成器测试必须逐项断言上述约束存在，不能只验证标题或文件非空。模板调整这些
规则后，`--check` 必须能够识别尚未更新的生成结果。

### 生成文件中的 Goal Mode 工作流

第二阶段生成的基础 `AGENTS.md` 必须包含当前根目录 `AGENTS.md` 的完整
`Goal Mode 工作流`。生成文件必须自包含，不能依赖模板仓库路径、外部链接或
“参见上级规范”等引用才能执行。至少需要逐字或等价保留以下组成部分：

1. 只有用户明确输入 `/goal`、明确要求 Goal Mode，或客户端已进入 Goal Mode
   时才启用；普通任务不得自动创建 Goal。
2. 使用客户端 Goal 工具注册目标，并在项目根目录按递增编号创建
   `goal-[num]/input.md`、`plan.md` 和 `tasks.md`。
3. `input.md` 逐字保存触发 Goal 的用户原始输入；`plan.md` 记录范围、验收、
   假设、风险、执行、验证和回滚；`tasks.md` 拆分可独立验证任务及检查节点。
4. Goal 初始化完成前不得修改实现；第一轮只能完成注册和三个文件初始化，最后
   只输出 `GOAL_INIT_DONE`。
5. 每轮开始完整读取三个 Goal 文件，只执行 `tasks.md` 中第一个未完成任务，
   不得跳过、合并或提前实现后续任务。
6. 每个任务完成后记录实际变更、验证证据、剩余风险和下一步；没有事实证据时
   不得声称已经完成或具有绝对信心。
7. 每完成三个实现任务执行一次跨任务全面检查，覆盖范围、架构、逻辑、竞态、
   资源、格式、分析、测试、构建、UI、安全、隐私、数据、文档和回滚。
8. 默认无人值守推进；只有需要新授权、真实凭据、破坏性操作、生产变更或会改变
   目标方向时才停止，并按 Goal 工具规则记录阻塞。
9. 保留当前工作流中的禁止事项，包括不抢占设备焦点、不影响网络或其他进程、
   不删除重要数据、不修改生产配置、不提前改实现、不扩大范围，以及不伪造验证。
10. 所有任务完成后执行最终全面 Review；修复所有已知高风险问题并记录证据后，
    才能将 Goal 标记完成。

“等价保留”只允许替换项目名称、路径或已经不存在的命令，不允许删除约束、降低
验证标准或改变执行顺序。实现时应把 Goal Mode 文本维护为一个可复用的规范片段，
由基础模板生成器引用，并在 CI 中比较根规范与生成模板对应章节；任一侧变化而另
一侧未同步时检查必须失败。

### 覆盖与可复现策略

1. 目标不存在时生成文件。
2. 目标与期望内容一致时成功退出，保持文件时间和内容不变。
3. 目标存在且内容不一致时必须失败并说明原因，不得静默覆盖用户修改。
4. 不提供隐式 `--force`；确需覆盖时由调用方先明确处理目标文件。
5. `--check` 不写文件：目标缺失或内容陈旧时返回非零，用于 CI。
6. 生成输入、模板和工具均提交版本库；相同输入必须产生逐字节相同输出。
7. 测试在临时目录执行，不得覆盖仓库根目录现有 `AGENTS.md`。

## 第二阶段任务顺序

正式 Goal 应按以下顺序细化，每轮仍只执行第一个未完成任务。

### Task 1：第二阶段基线与依赖复核

## 回滚原则

1. 屏幕适配回滚必须同时恢复根节点初始化、项目设计单位、主题尺寸、Feature
   使用点、依赖约束和锁文件，不能只删除 `flutter_screenutil`。
2. 认证回滚不得遗留凭据、路由重定向或普通存储中的敏感字段。
3. 资源生成回滚恢复源资源、配置和全部生成产物，避免 Android/iOS 漂移。
4. `AGENTS.md` 生成器回滚只移除专用工具、模板、测试和初始化调用；不得删除或
   覆盖已经属于下游项目的 `AGENTS.md`。
5. 任何破坏性迁移都必须附独立迁移说明，并在临时副本验证回滚命令。
